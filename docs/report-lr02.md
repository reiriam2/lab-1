## 3. Security-сценарій (SQL Injection)

### 3.1. Гіпотеза

Використання конкатенації вхідних рядків у методі `FromSqlRaw` дозволяє зловмиснику маніпулювати структурою SQL-запиту, впроваджуючи довільні логічні оператори.

### 3.2. Уразливий стан

У файлі `src/SecureLab.Api/Scaffolding/Lab02Endpoints.cs` було виявлено такий уразливий код:

```csharp
var sql = "SELECT * FROM incidents WHERE title ILIKE '%" + (q ?? "")
    + "%' OR description ILIKE '%" + (q ?? "") + "%' ORDER BY " + order + " LIMIT 50";
```

### 3.3. Мінімальний локальний PoC (сценарій C)

Для перевірки уразливості було використано запит із корисним навантаженням:

```text
?q=zz-no-match%27%20OR%20TRUE%20--%20
```

### 3.4. Спостереження

Замість порожньої відповіді база даних повернула статус `200 OK` і всі 5 записів із таблиці. Це сталося через те, що апостроф закрив рядковий літерал, а умова `OR TRUE` зробила вибірку масовою.

Запит із легітимним апострофом (`O'Brien`, сценарій D) спричиняв помилку бази даних зі статусом `500 Internal Server Error`.

### 3.5. Першопричина

Основною причиною уразливості стало змішування коду та даних через пряму конкатенацію вхідних параметрів `q` та `sortBy` у сирий SQL-запит без використання параметризації.

### 3.6. Виправлення

Для усунення SQL Injection було реалізовано такі зміни:

- Перехід на безпечний механізм EF Core через `EF.Functions.ILike` із передаванням значення окремим параметром.
- Екранування спеціальних символів (`%`, `_`, `\`) за допомогою допоміжної функції `EscapeLike`.
- Впровадження суворого серверного білого списку (`allowlist`) для параметра сортування `sortBy`.

### 3.7. Повторна перевірка та позитивна регресія

Після виправлення ін'єкційні запити повертають порожній результат `[]`, легітимні пошукові запити опрацьовуються успішно зі статусом `200 OK`, а некоректне сортування повертає `400 Bad Request`.

### 3.8. Залишковий ризик

Усунення SQL Injection у конкретному endpoint не скасовує потреби впровадження глобальних механізмів автентифікації, авторизації на основі ролей (RBAC) та обмеження частоти запитів (`rate limiting`).

## 5. Обмеження і висновок

**Обмеження.** Використання перевірки дублікатів на рівні LINQ (`AnyAsync`) не гарантує захисту від гонок даних (`race conditions`) за умов високого рівня паралелізму без накладання унікального індексу в базі даних або використання транзакцій із відповідними рівнями ізоляції.

**Висновок.** У ході виконання лабораторної роботи було успішно виявлено, задокументовано та усунено уразливість SQL Injection за допомогою безпечних механізмів EF Core та суворого білого списку сортування. Реалізована валідація вхідних даних і автоматичні інтеграційні тести забезпечують надійніший захист бекенду від типових векторів атак.
